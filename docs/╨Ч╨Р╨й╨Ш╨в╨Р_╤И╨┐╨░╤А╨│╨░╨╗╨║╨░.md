# Подготовка к устной защите (Assignment 3)

Защита даёт 10 из 20 баллов. 5 вопросов, по 2 балла за каждый. Отвечать своими словами и опираться на конкретику из отчёта.

## Q1. Почему дизайн подходит к RQ
- RQ про эффект **одного** элемента интерфейса (метка). Рандомизированный эксперимент с двумя группами (between-subjects) изолирует этот элемент: картинки, текст и вёрстка одинаковые, отличается только метка.
- Единица анализа — **участник**. Шесть оценок усредняются в один балл authenticity и один балл trust, поэтому повторные оценки не считаются независимыми наблюдениями.
- Дизайн даёт числа: разницу средних с 95% CI и Hedges' g.
- Отвергнутая альтернатива — within-subjects: участник увидит один и тот же профиль с меткой и без неё, догадается о манипуляции, появятся carry-over и demand effects.

## Q2. Выборка и bias
- Около 60 студентов AITU 18–25 с опытом дейтинг-приложений, 30 на группу. Набор добровольцев (convenience), затем случайное распределение по группам.
- Это пилот, а не power-расчёт: при n = 30 надёжно ловится только d ≈ 0,74 (проверено в скрипте: 0,736).
- Bias: самоотбор, знакомые, один вуз. Как снижаем: приглашение не упоминает метку, набор с разных факультетов и курсов, рандомизация, честные ограничения на обобщение.

## Q3. Инструмент / процедура (выбрать одно и знать до конца)
- **Блочная рандомизация**: блоки по 4 (2 с меткой, 2 без), последовательность заранее генерируется из seed 20261022 и хранится в БД. Поэтому группы почти равны в любой момент набора (T3: дисбаланс никогда не больше 2). Тестовые сессии идут из отдельного потока.
- **Шкалы**: по 3 пункта (1–7) на authenticity и на trust. Надёжность проверяется через Cronbach's α. Шкалы не объединяются в одну.
- **Manipulation check**: вопрос «заметил(а) ли метку?» задаётся *после* всех оценок, чтобы не подсказывать.

## Q4. Анализ одной цели
- **Objective 3**: на каждого участника средний балл, затем группа с меткой против группы без метки. Считаем разницу средних с 95% CI по Welch, Hedges' g с интервалом, поправку Holm на 2 исхода, Mann–Whitney как проверку устойчивости. Отдельный sensitivity-анализ без тех, кто метку не заметил.
- **Objective 1**: тесты T1–T3 (pass/fail), а не статистика.
- Незначимый результат пилота ≠ «эффекта нет».

## Q5. Практическая часть + ограничение (показать вживую!)
- Запустить `python app.py`, открыть `http://127.0.0.1:5000/?test=1`, пройти один профиль, показать метку. Потом `python -m pytest -v -rxs tests/`.
- Объяснить одно решение: **пустой слот одинаковой высоты** в группе без метки. Так вёрстка не сдвигается (T2c проверяет геометрию), и разница в оценках не может объясняться сдвигом макета.
- **Failure case (T6)**: на телефоне 360 px радиокнопки 13×13 px (ячейка 21 px), это меньше минимума WCAG 2.2 в 24×24 px. Риск: промахи по кнопкам → ошибка измерения. Исправление: кликабельная ячейка ≥ 44 px или один пункт на строку.
- Нерешённое: изображения пока заглушки. Нужны лицензированные синтетические лица, подобранные по привлекательности (Makowski et al., 2025), потом пересчёт хэшей.
- Этика: согласие, study code вместо имени, согласие хранится отдельно от ответов, неподходящие посетители не сохраняются, нет IP/e-mail, debrief раскрывает манипуляцию. Этическое одобрение ещё не получено, реальных данных нет.
